# 運用（自動更新・リンク確認・配信）

最終更新: 2026-10-25

現在の運用の正本。`パイプライン.md`・`公開チェックリスト.md` の VPS/cron 前提の記述は古く、
実際は **すべて GitHub Actions（クラウド）** で動いている。

## 自動で動いているもの

| ワークフロー | いつ | 何をする |
|---|---|---|
| `deploy.yml`（ビルドしてFTP公開） | main に push（src/・static/・DB の変更） | build.py → FTP配信 |
| `probe.yml`（リンク死活監視） | 毎日 JST 3:30 | probe.py で 2,500 リンク確認 → DB・月次CSVをコミット → 配信 |
| `soumu.yml`（総務省の財政データ） | 毎月4日 JST 4:17 | 決算カード・類似団体区分・主要財政指標を取得。内容が変わったときだけコミット → 配信 |

### 配信（FTP）の決まりごと

- 3つとも配信ジョブは同じグループ `tdf47-ftp` で **1本ずつ** 実行する。実行中の配信は止めない
  （途中で止めるとサーバーが中途半端になる）。待機中の配信は新しいものに置き換わるが、
  各配信は開始時点の **main の最新** を取得するので取りこぼしはない。
- FTP のタイムアウトは 120 秒。1回目が失敗したら1回だけやり直す。
- ビルド結果は、中身が同じなら毎回まったく同じになる（CSS/JS の `?v=` は static/ の中身のハッシュ）。
  そのため配信されるのは変わったファイルだけ。
  - 例外: サイドバーに「リンク ○件」（link テーブルの総数）が出ているため、
    **リンクを追加・削除したときは全ページが変わり、全ファイル配信（約40分）** になる。

## リンク確認（probe.py）

- 1日 2,500 件。順番は「最後に確認を**試みた**日時」が古い順（一度も試していないものが最優先）。
  対象（URLあり・ok/unchecked/dead）約 12,800 件を約6日で一巡する（robots.txt で断られる分は通信しないので実際はもっと早い）。
- robots.txt で断られたリンクは確認しない（マナー）。試みた記録だけ probe に残し（error=`robots.txt で不許可`）、
  順番を後ろに回す。状態（status）は変えない。
- 判定:
  - 200 → `ok`、最終確認日を更新
  - 判定できない応答 → リンク切れにしない（`ok` はそのまま、それ以外は `unchecked`）。最終確認日は更新しない
    - ぎょうせい（d1-law.com）・第一法規（legal-square.com）の 401/403/429・SSL失敗・切断・タイムアウト
      （人がブラウザで開くと見られるが、プログラムからは拒否される）
    - 中間証明書を送らないサーバー（`unable to get local issuer certificate`）。どのホストでも
    - 200以外の成功応答（202 など。ボット対策の確認画面で返ることがある）。どのホストでも
  - 一時的な不調の可能性がある失敗（時間切れ・接続の切断・502/503/504） → 1回目はリンク切れにしない（扱いは上と同じ）。
    前回の確認でも失敗していたとき（2回続けて失敗。前回が「判定できない」応答なら数えない）に `dead`。確認は約6日で一巡するので、本当に切れたリンクが
    消えるまでは最大で一巡分遅れる
  - それ以外（404・500・ドメイン消滅など） → `dead`（画面には出さない）
- 国内からの再確認（2026-10-28〜）: 確認は GitHub（海外）で動くため、海外からの接続を断っている自治体サイトは毎回
  時間切れになる。応答が無い失敗（時間切れ・接続拒否・切断など）だけを、tdf47.com のサーバーに置いた窓口
  `/_recheck/`（`src/server/recheck.php`）に国内から確認し直してもらい、その結果で上の判定をする。
  - 合言葉は GitHub の秘密情報 `RECHECK_TOKEN`。配信時にハッシュだけを `_recheck/config.php` に書く（公開リポジトリには入れない）
  - 窓口が使えないとき（合言葉なし・応答なし・窓口側で断ったとき＝422）は、今までどおり海外からの結果で判定する
  - 国内からも「名前を引けない・SSL・その他の通信エラー」だったときは、窓口側の事情のこともあるので使わず、海外からの結果で判定する
  - 1回の確認で窓口に頼むのは最大60件。窓口が3回続けて使えなかったら、その回は国内からの確認をやめる（全体の時間を守るため）
  - 国内から確認できた公式サイトは、SNSの掲載照合をしない（本文を受け取らないため）
  - 国内のレンタルサーバーからもつながらないサイトもある（例：長野県後期高齢者医療広域連合の例規集、2026-10-28）
  - 動作確認は手動のワークフロー「国内からの再確認窓口を試す」（URLを指定。DBは変えない）
- robots.txt で断られるのは約4,140件（2026-10-25 調査）：公式SNS 3,472件（Facebook・Instagram・X。LINE・YouTube は許可）、
  議会会議録 660件（kaigiroku.net・db-search.com・dbsr.jp の会議録システム）ほか。
  - 直近の確認が「robots.txt で不許可」で最終確認日が無いリンクは、画面に「自動確認の対象外」と出す
    （理由「提供元が自動確認を許可していません」はマウスを載せたときの表示＝title 属性。カードの高さは変えない）
  - 公式SNSは、公式サイトのトップページを確認したときに、そのアカウントへのリンクが載っているかを照合して
    probe に記録する（error=`公式サイトに掲載あり`／`公式サイトに掲載なし`。画面には出さない）。
    「掲載あり→掲載なし」に変わったものだけ月次レビューCSVに載せる。link の状態・最終確認日は変えない
  - この照合の記録は「確認の試み」に数えない（巡回の順番・前回との比較・誤判定の見直しに使わない）。履歴は別枠で直近3回分
- 毎回の開始時に、既存の確認結果から上の「判定できない」「一時的な失敗が1回だけ」に当たる `dead` を `unchecked` に戻す（`--reclassify-only` で単独実行可）。
- 確認履歴（probe テーブル）は 1リンクにつき直近3回分だけ残す（DB が毎日コミットされるため）。
  robots.txt 不許可の記録・公式サイト掲載の照合は別枠でそれぞれ3回分（通常の確認の履歴を押し出さない）。
- 例規集が見つからない団体（25団体＋北方領土6村）は「リンクを収集中です」のまま（「該当なし」にはしない）。

### 月次レビュー CSV

`reports/monthly-review-YYYYMM.csv` に、その月に変化があった確認結果を **日々追記** する（git 管理）。
列: 確認日時・団体コード・団体名・種別・前の状態・新しい状態・リンクID・URL・HTTP・最終URL・タイトル・エラー・変化フラグ。
月1回目視して、リンク切れの移転先を探す材料にする。

## 人手で確認したリンク（manual_links.csv）

全国リンク集（RILG・uub 等）に無い／移転していた URL は、公式サイトで確認したうえで
`src/ingest/manual_links.csv` に1行ずつ記録し、`python3 src/ingest/15_manual_links.py` で DB に入れる。

- 列: `entity_code, kind_code, url, evidence（確認したページ）, checked_on, note`
- 入れた行は `unchecked`（翌日以降の probe が確認して `ok` にする）。同じ URL が `dead` だった場合は `unchecked` に戻す。
- 2026-10-25 時点: 例規集 30 団体、広報誌 35 団体、公式サイト 1 団体（富岡市）。

### 候補ページの確認（check_pages.py）

- 手動のワークフロー「候補ページを開いて確かめる」。入力 CSV（entity_code,kind_code,url,memo）の各 URL を開き、
  HTTP の結果・最終 URL・題名・指定の言葉を含むリンクを `reports/check-result-<日時>.csv` にコミットする（DB は変えない）。
- 調べ物の道具（WebFetch）では開けない自治体サイトも、クラウドから開いて確かめられる。結果を見て manual_links.csv に入れる。
- 「公式サイトから項目のページを探す」は `kinds` に `kouhou,reiki` を指定すると広報誌・例規集の候補も探せる（再調査用）。

## 議会会議録「該当なし」の表示

`gikai` の `none`（892団体）は「会議録検索システムが無い」という意味で、会議録そのものが無いわけではない。
画面の文言は「会議録検索システムはありません。会議録は公式サイトの議会ページで公開されている場合があります」。

## 一時的な調査をクラウドで回すとき

自治体サイトはこの作業環境（クラウドのコンテナ）からは繋がらない。調べものは一時ブランチ
（例 `tmp/kouhou-scan`）にスクリプトと、そのブランチへの push で動くワークフローを置き、結果を同じブランチにコミットさせて読む。
終わったらブランチは削除する（作業環境からは削除できないので GitHub の画面で）。
